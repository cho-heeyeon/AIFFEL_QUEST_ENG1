# MLOps Day 1 — Full Stack Deep Learning과 ML 프로젝트 기획

## Chapter 0. Introduction — 모델 배포, MLOps, 그리고 Full Stack Deep Learning

### ✅ Chapter 0 체크포인트

#### 1. 모델 배포, Full Stack DL, MLOps는 각각 어떤 범위를 담당하며, 왜 세 과정이 분리되어야 하는가?

세 과정은 서로 연결되어 있지만 담당하는 범위가 다르다.

* **모델 배포(Model Deployment)**
  학습된 모델을 실제 사용자가 사용할 수 있도록 API나 UI 형태로 서비스하는 과정이다.
  예를 들어 FastAPI를 이용해 `/predict` API를 만들고, Streamlit을 이용해 사용자가 모델에 데이터를 입력하고 결과를 확인할 수 있는 화면을 만들 수 있다.

* **Full Stack Deep Learning**
  좋은 모델을 만드는 것뿐만 아니라 데이터 수집, 모델 개발, 배포, 사용자 피드백 등 **ML 제품 전체를 설계하는 관점**을 다룬다.

* **MLOps**
  배포된 ML 시스템을 지속적으로 운영하기 위한 자동화와 관리에 초점을 둔다.
  모델 버전 관리, 데이터 관리, 모니터링, 재학습, 테스트, CI/CD 등이 대표적이다.

따라서 학습 흐름을 단순화하면 다음과 같다.

```text
모델 개발
   ↓
모델 배포
   ↓
ML 제품 전체 구조 이해 (Full Stack DL)
   ↓
지속적인 운영·관리·자동화 (MLOps)
```

세 과정은 목적과 범위가 다르기 때문에 분리하여 학습할 필요가 있다.

---

#### 2. "평평한 지구 ML"과 "둥근 지구 ML"의 차이는 무엇인가? 데이터 플라이휠은 어디에 해당하는가?

**평평한 지구 ML**은 ML 개발을 한 방향으로 끝나는 과정으로 생각하는 방식이다.

```text
데이터 → 학습 → 모델 → 배포 → 끝
```

반면 **둥근 지구 ML**은 모델 배포 이후 실제 사용 과정에서 새로운 데이터를 얻고, 이를 다시 모델 개선에 사용하는 순환 구조이다.

```text
데이터
 ↓
모델 학습
 ↓
배포
 ↓
사용
 ↓
새로운 데이터 수집
 ↓
모델 개선
 └────────→ 반복
```

이러한 반복 구조가 **데이터 플라이휠(Data Flywheel)**이다.

즉, 서비스를 사용할수록 데이터가 축적되고, 데이터가 모델을 개선하며, 개선된 모델이 다시 제품의 가치를 높이는 선순환 구조이다.

---

#### 3. ML Powered Product와 MLOps의 지향점 차이는 무엇인가?

두 개념은 다음 질문으로 구분할 수 있다.

**ML Powered Product**

> "ML을 이용하여 사용자에게 어떤 가치를 제공할 것인가?"

예를 들어 제조 현장에서는 ML을 이용하여 검사 자동화나 이상 탐지를 구현할 수 있다.

**MLOps**

> "이 ML 시스템을 실제 환경에서 어떻게 안정적으로 운영하고 지속적으로 개선할 것인가?"

따라서 ML Powered Product가 **제품의 가치**에 초점을 둔다면 MLOps는 **운영의 안정성과 지속 가능성**에 초점을 둔다.

---

# Chapter 1. ML 제품의 가치와 현대 ML 생태계의 지형도

## ✅ Chapter 1 체크포인트

### 1. Software 1.0과 Software 2.0의 근본적인 차이는 무엇인가?

**Software 1.0**은 개발자가 규칙을 직접 코드로 작성한다.

```python
if diameter < 20.010:
    result = "NG"
elif diameter > 20.030:
    result = "NG"
else:
    result = "OK"
```

반면 **Software 2.0**에서는 사람이 모든 규칙을 직접 작성하기보다 데이터로부터 모델이 패턴을 학습한다.

```text
데이터 + 학습 알고리즘
        ↓
      모델
        ↓
      예측
```

Software 1.0은 코드가 동일하면 같은 동작을 기대하기 쉽지만, Software 2.0은 데이터와 모델 변화에 따라 결과가 달라질 수 있다.

따라서 ML 시스템에서는 코드 테스트뿐만 아니라 **데이터 검증, 모델 성능 검증, 드리프트 모니터링, 재학습 관리** 등이 추가로 필요하다.

---

### 2. CACE 현상이 ML 시스템에서 중요한 이유는 무엇인가?

CACE는 **Changing Anything Changes Everything**, 즉 하나를 변경하면 시스템의 다른 부분까지 영향을 받을 수 있다는 의미이다.

전통적인 소프트웨어는 일반적으로 특정 코드의 변경 범위와 영향을 비교적 명확하게 추적할 수 있다.

그러나 ML 시스템에서는 다음 요소들이 서로 연결되어 있다.

```text
데이터
 ↕
피처
 ↕
모델
 ↕
임계값
 ↕
예측 결과
 ↕
사용자 경험
```

예를 들어 카메라 조명이 바뀌면 입력 영상의 특성이 달라지고, Edge 검출이나 모델 예측 성능까지 영향을 받을 수 있다.

따라서 ML 시스템에서는 작은 변경이라도 전체 파이프라인에 미치는 영향을 검증해야 한다.

---

### 3. 기술의 범용화가 ML 엔지니어의 역할을 어떻게 변화시키는가?

과거에는 모델 자체를 구현하는 능력이 매우 중요했다.

현재는 PyTorch, TensorFlow, Hugging Face, 사전학습 모델, 클라우드 API 등 다양한 기술을 쉽게 활용할 수 있다.

따라서 ML 엔지니어의 역할은 단순히 모델을 만드는 것에서 다음과 같이 확대되고 있다.

```text
모델 개발
   ↓
데이터 관리
   ↓
시스템 통합
   ↓
배포
   ↓
모니터링
   ↓
지속적인 개선
```

즉, **어떤 기술을 선택하고 실제 문제 해결에 어떻게 연결할 것인지**가 더욱 중요해지고 있다.

# Chapter 2. ML 도입 여부 결정과 우선순위 설정

## ✅ Chapter 2 체크포인트

### 1. 관심 있는 ML 프로젝트를 실현 가능성 × 임팩트 매트릭스에 배치한다면?

관심 프로젝트를 **YOLO + OpenCV 기반 샤프트 외경 자동 측정 시스템**으로 설정하였다.

이 프로젝트는 성공할 경우 수작업 검사의 자동화, 검사 일관성 향상, 측정 데이터 자동 저장 등의 효과를 기대할 수 있으므로 **임팩트가 높은 프로젝트**라고 판단한다.

다만 실제 제조 현장에서 요구되는 측정 정밀도를 만족하기 위해서는 카메라, 렌즈, 조명, Calibration, 데이터 확보 및 반복 측정 검증 등이 필요하다.

따라서 현재 단계에서는 다음과 같이 평가할 수 있다.

```text
실현 가능성 : 중간
임팩트      : 높음
```

즉, **고임팩트이지만 기술적 검증이 추가로 필요한 영역**에 위치한다고 판단한다.

---

### 2. "API로 충분한가?"를 판단하기 위해 무엇을 확인해야 하는가?

다음 항목을 확인해야 한다.

1. 필요한 기능을 API가 제공하는가?
2. 요구하는 정확도를 만족하는가?
3. 데이터 보안 문제가 없는가?
4. 응답 속도가 충분한가?
5. 사용 비용이 적절한가?
6. 커스터마이징이 가능한가?
7. 외부 API 장애가 발생했을 때 대응할 수 있는가?

제조 현장의 민감한 이미지나 품질 데이터를 사용하는 경우에는 외부 API 사용보다 자체 구축이 더 적합할 수도 있다.

---

### 3. ML 도입 전에 고려할 수 있는 4가지 대안

ML을 사용하기 전에 다음과 같은 방법을 먼저 검토할 수 있다.

1. **사람이 직접 처리**
   작업량이 적고 전문적인 판단이 필요한 경우 적합하다.

2. **규칙 기반 프로그램**
   판단 기준이 명확한 경우 ML보다 단순하고 안정적일 수 있다.

3. **기존 소프트웨어 또는 솔루션 구매**
   이미 검증된 상용 솔루션이 있다면 개발 비용과 시간을 줄일 수 있다.

4. **외부 API 사용**
   OCR, 번역, 음성인식 등 이미 범용 기술이 충분히 발전한 분야에서 유용하다.

따라서 ML은 항상 첫 번째 해결 방법이 아니라 **문제와 비용을 검토한 후 선택해야 하는 방법 중 하나**이다.

# Chapter 3. ML 프로젝트 라이프사이클

## ✅ Chapter 3 체크포인트

### 1. ML 프로젝트 라이프사이클 4단계

```text
① 프로젝트 기획
      ↓
② 데이터 수집·라벨링
      ↓
③ 모델 학습·개발
      ↓
④ 배포·운영
```

각 단계의 핵심 활동은 다음과 같다.

* **기획:** 해결할 문제와 성공 기준을 정의한다.
* **데이터:** 필요한 데이터를 확보하고 품질을 확인한다.
* **모델 개발:** 데이터를 이용하여 모델을 학습하고 평가한다.
* **배포·운영:** 실제 환경에서 모델을 서비스하고 성능을 모니터링한다.

---

### 2. 4단계에서 2단계로 되돌아가는 이유는 무엇인가?

실제 환경에 모델을 배포하면 학습 과정에서 발견하지 못했던 새로운 데이터와 조건이 나타날 수 있다.

예를 들어 제조 비전 시스템에서는 다음과 같은 변화가 발생할 수 있다.

* 조명 변화
* 카메라 위치 변화
* 제품 표면 상태 변화
* 새로운 불량 유형
* 기존 학습 데이터에 없던 조건

따라서 배포 후 모델 성능이 충분하지 않으면 새로운 데이터를 다시 수집해야 한다.

이를 예방하려면 기획 단계에서 다음 질문이 필요하다.

> "실제 운영 환경의 데이터를 충분히 대표하는 학습 데이터를 확보할 수 있는가?"

---

### 3. 자연적인 데이터 플라이휠과 인위적인 데이터 플라이휠의 차이

추천 서비스나 검색 서비스는 사용자의 클릭, 검색, 구매 등의 행동이 자연스럽게 데이터로 축적된다.

```text
사용 → 행동 데이터 → 모델 개선 → 추천 개선 → 더 많은 사용
```

반면 제조 검사 시스템에서는 사용자가 자동으로 라벨을 만들어 주지 않는다.

따라서 검사 결과와 실제 측정값, 불량 판정 등을 별도로 저장하여 데이터 플라이휠을 **의도적으로 설계해야 한다.**

---

# Chapter 4. ML 제품의 3가지 아키타입

## ✅ Chapter 4 체크포인트

### 1. 세 가지 아키타입의 예

* **Software 2.0:** 이미지 분류 시스템
* **Human-in-the-loop:** AI가 판독 결과를 제시하고 사람이 최종 승인하는 품질 검사 시스템
* **Autonomous:** 충분히 검증된 후 자동으로 판단하고 후속 작업까지 수행하는 자동 검사 시스템

---

### 2. Human-in-the-loop에서 Autonomous로 발전하는 과정

초기에는 AI의 판단을 사람이 검토한다.

```text
AI 측정
   ↓
작업자 확인
   ↓
최종 판정
```

충분한 데이터와 검증 결과가 축적되고 신뢰성이 확보되면 다음 단계로 발전할 수 있다.

```text
자동 측정
   ↓
자동 판정
   ↓
결과 저장
   ↓
설비/공정과 연동
```

전환을 위해서는 모델 성능뿐 아니라 **실패 비용, 안전성, 측정시스템 검증, 예외 처리 및 운영 안정성**을 함께 확인해야 한다.

---

### 3. 내가 만들고 싶은 ML 제품은 어떤 아키타입인가?

샤프트 외경 자동 측정 시스템의 초기 단계는 **Human-in-the-loop** 방식이 적합하다고 판단한다.

샤프트 외경은 품질과 안전에 관련된 중요한 측정값이므로 초기부터 완전 자동 판정을 수행하기보다 시스템의 측정 결과를 작업자가 확인하도록 설계하는 것이 적절하다.

충분한 현장 데이터와 반복 검증을 통해 신뢰성이 확보된 이후 Autonomous 단계로 확대할 수 있다.

---

# Chapter 5. ML 프로젝트 팀 구성과 조직 설계

## ✅ Chapter 5 체크포인트

### 1. ML 프로젝트에 필요한 5가지 역할

일반적으로 다음과 같은 역할이 필요하다.

1. 제품/프로젝트 담당
2. 데이터 엔지니어
3. 데이터 사이언티스트 또는 ML 연구자
4. ML 엔지니어
5. 소프트웨어/인프라 엔지니어

풀스택 ML 엔지니어는 프로젝트 환경에 따라 데이터 처리, 모델 개발, API 개발, 배포 및 모니터링 등 여러 영역을 연결할 수 있다.

다만 모든 분야의 전문성을 한 사람이 완전히 대신한다는 의미는 아니다.

---

### 2. "리서치와 프로덕션의 거리를 좁혀라"는 의미

연구팀이 모델 정확도만 높이고 개발팀이 나중에 별도로 배포하는 구조에서는 실제 서비스 전환 과정에서 문제가 발생하기 쉽다.

따라서 초기 단계부터 다음 요소를 함께 고려해야 한다.

```text
모델 성능
+ 실제 데이터
+ API
+ 서비스 환경
+ 운영 조건
+ 모니터링
```

즉, **모델 개발 단계부터 실제 운영 환경을 고려해야 한다**는 의미이다.

# Chapter 6. ML 프로젝트 기획의 실전 체크리스트

## ✅ Chapter 6 체크포인트

### 1. 프로젝트에서 가장 답하기 어려운 질문 3가지

샤프트 외경 측정 프로젝트를 기준으로 다음 세 가지가 어렵다고 판단한다.

**① 실제 현장 데이터를 충분히 확보할 수 있는가?**

다양한 촬영 조건과 제품 상태를 포함하는 데이터가 필요하기 때문이다.

**② 요구 측정 정확도를 안정적으로 만족할 수 있는가?**

카메라, 렌즈, 조명, Calibration 및 제품 표면 상태 등이 측정 결과에 영향을 줄 수 있기 때문이다.

**③ PoC 결과를 실제 양산 환경에서도 재현할 수 있는가?**

개발 환경에서 성공한 결과가 실제 생산라인의 변화 조건에서도 동일하게 유지되는지는 별도의 검증이 필요하기 때문이다.

---

### 2. 고임팩트 프로젝트를 찾는 4가지 멘탈 모델 적용

**예측 비용 하락**

자동 측정을 통해 반복적인 수작업 검사의 부담을 줄일 가능성이 있다.

**마찰 감소**

측정 → 판정 → 기록 과정을 자동화하면 수작업 입력 과정을 줄일 수 있다.

**Software 2.0**

복잡한 영상 조건을 사람이 모든 규칙으로 정의하기 어려운 부분에 학습 기반 비전 모델을 활용할 수 있다.

**업계 벤치마킹**

머신비전과 자동 검사 기술이 실제 제조업에서 어떻게 활용되는지 조사하여 프로젝트의 기술적 방향을 결정할 수 있다.

---

### 3. 정확도를 높일수록 비용이 증가한다는 것은 어떤 의미인가?

높은 정확도를 요구할수록 다음과 같은 비용이 증가할 수 있다.

* 더 많은 데이터
* 더 정확한 라벨
* 고성능 카메라
* 텔레센트릭 렌즈
* 안정적인 조명
* 정밀 Calibration
* 반복 측정 검증
* 개발 및 유지관리 시간

따라서 무조건 최고 정확도를 목표로 하기보다 **제품과 공정에서 실제로 필요한 정확도를 먼저 정의해야 한다.**

또한 확신도가 낮거나 측정 조건이 비정상적인 경우 사람에게 판정을 넘기는 Human-in-the-loop 방식으로 시스템을 설계하면 초기 자동화 단계의 위험을 줄일 수 있다.

---

### 4. "당신은 구글이 아니다"라는 원칙의 의미

프로젝트 초기부터 복잡한 대규모 MLOps 플랫폼을 구축할 필요는 없다.

현재 필요한 도구의 예는 다음과 같다.

```text
Python
OpenCV
YOLO
Git/GitHub
FastAPI
Docker
간단한 데이터/로그 저장
```

프로젝트 규모가 커지고 운영 요구가 명확해진 이후 다음과 같은 도구를 검토할 수 있다.

```text
MLflow
Airflow
Kubernetes
대규모 Feature Store
복잡한 CI/CD
자동 재학습 파이프라인
```

즉, **현재 문제를 해결하는 데 필요한 최소한의 시스템부터 구축하고 필요에 따라 확장하는 것이 중요하다.**

# ✅ Day 1 통합 체크포인트 — 오늘 배운 것을 하나로 꿰기

## 1. 파이프라인 위치 인식

학습 경로를 다음과 같이 이해하였다.

```text
모델 개발
    ↓
모델 배포
    ↓
Full Stack Deep Learning
    ↓
MLOps
```

모델 배포 과정에서는 학습된 모델을 API와 UI를 통해 사용할 수 있도록 만드는 방법을 배운다.

그러나 실제 ML 제품은 단순히 API를 만드는 것으로 끝나지 않는다. 어떤 문제를 해결할 것인지, 데이터를 어떻게 확보할 것인지, 사용자의 피드백을 어떻게 다시 모델 개선에 사용할 것인지까지 고려해야 한다.

Full Stack Deep Learning은 이러한 **모델과 실제 제품 사이의 연결 과정**을 이해하게 해준다.

그 이후 MLOps에서는 완성된 ML 시스템을 지속적으로 테스트하고 모니터링하며 업데이트하는 방법을 다룬다.

따라서 Full Stack DL은 **모델 배포와 MLOps를 연결하는 단계**라고 이해하였다.

---

## 2. 종합 기획

프로젝트는 **YOLO + OpenCV 기반 샤프트 외경 자동 측정 시스템**으로 설정하였다.

### (1) ML이 정말 필요한가?

샤프트 위치가 일정하지 않거나 촬영 조건에 변화가 있는 경우 측정 대상 영역을 안정적으로 찾는 데 객체 탐지 모델을 활용할 가능성이 있다.

다만 외경 계산 자체는 반드시 ML이어야 하는 것은 아니며 OpenCV와 Calibration 같은 전통적인 머신비전 방법을 함께 사용할 수 있다.

따라서 이 프로젝트는 **ML + 규칙 기반 영상처리의 하이브리드 구조**가 적합하다.

### (2) Build / Buy / API 중 무엇인가?

제조 현장의 측정 정밀도, 데이터 보안, 카메라 환경 및 사용자 정의 측정 로직을 고려하면 우선 **Build 방식의 PoC**가 적합하다고 판단하였다.

### (3) 아키타입은?

초기 단계:

```text
Human-in-the-loop
```

충분한 검증 이후:

```text
Autonomous
```

로 발전시키는 것을 목표로 한다.

### (4) 실현 가능성 × 임팩트

```text
실현 가능성 : 중간
임팩트      : 높음
```

으로 판단한다.

### (5) 비용의 주요 동인

이 프로젝트에서는 특히 다음 요소가 비용에 큰 영향을 줄 것으로 예상한다.

* 데이터 확보 및 라벨링
* 카메라·렌즈·조명 등 측정 환경 구축
* 높은 측정 정밀도를 확보하기 위한 검증 및 Calibration

### (6) PoC 종료 조건

PoC 단계에서는 다음 사항을 사전에 정의해야 한다.

* 목표 측정 오차
* 반복 측정 안정성
* 다양한 촬영 조건에서의 성능
* 처리 시간
* 실패 사례 및 예외 처리 기준

이 기준을 충족했을 때 다음 단계의 현장 검증으로 진행한다.

## 3. 둥근 지구 설계 — 데이터 플라이휠

샤프트 측정 시스템의 데이터 플라이휠을 다음과 같이 설계할 수 있다.

```text
샤프트 촬영
     ↓
YOLO ROI 탐지
     ↓
OpenCV 외경 측정
     ↓
측정값 및 OK/NG 판정
     ↓
작업자 확인 또는 기준 측정값 비교
     ↓
이미지 + 측정값 + 판정 결과 저장
     ↓
오류 사례 분석
     ↓
데이터셋 추가
     ↓
모델/알고리즘 개선
     ↓
측정 신뢰성 향상
     └──────────────→ 반복
```

제조 시스템에서는 사용자 행동만으로 정답 데이터가 자동 생성되지 않으므로, 기준 측정값과 작업자의 확인 결과를 함께 저장하도록 **데이터 플라이휠을 의도적으로 설계해야 한다.**

## 4. 실패 시나리오

이 프로젝트에서 가능성이 높은 실패 원인 중 하나는 **개발 환경에서의 성능이 실제 생산 환경에서 재현되지 않는 것**이다.

예를 들어 다음과 같은 변화가 원인이 될 수 있다.

```text
조명 변화
카메라 위치 변화
제품 표면 반사
제품 위치 변화
새로운 제품 상태
Calibration 변화
```

이는 **기술적 비실현성 또는 프로덕션 전환 실패**로 이어질 수 있다.

이를 방지하기 위해 기획 단계에서 다음 질문을 명확히 해야 한다.

> "실제 생산 환경에서 발생 가능한 조건을 데이터와 시험 조건에 충분히 포함했는가?"

또한 PoC와 실제 현장 검증을 구분하여 진행해야 한다.

## 5. 기술적 부채 예측

시스템을 배포한 후 시간이 지나면 다음과 같은 기술적 부채가 발생할 수 있다.

### CACE

카메라, 조명, ROI, 모델 또는 Calibration 중 하나를 변경했을 때 전체 측정 결과가 달라질 수 있다.

### 데이터 드리프트

시간이 지나면서 제품의 표면 상태, 생산 조건, 카메라 환경 등이 기존 학습 데이터와 달라질 수 있다.

### 외부 세계의 불안정성

카메라 위치, 조명 밝기, 설비 진동, 네트워크, 서버 상태 등 모델 외부의 요소가 시스템 결과에 영향을 줄 수 있다.

샤프트 외경 자동 측정 시스템에서는 특히 **입력 영상 조건의 변화와 Calibration 변화가 측정 결과에 직접 영향을 줄 가능성이 있으므로 지속적인 모니터링이 중요하다.**

따라서 배포 이후에도 다음과 같은 순환 구조가 필요하다.

```text
운영
 ↓
데이터 및 측정 결과 저장
 ↓
성능 모니터링
 ↓
이상 사례 분석
 ↓
데이터 추가
 ↓
모델/알고리즘 검증 및 개선
 ↓
재배포
```

# Day 1 학습 정리

이번 학습을 통해 ML 프로젝트는 단순히 **좋은 모델을 만드는 것으로 끝나는 것이 아니라는 점**을 이해하였다.

```text
문제 정의
  ↓
ML 도입 여부 판단
  ↓
데이터 확보
  ↓
모델 개발
  ↓
배포
  ↓
사용
  ↓
데이터 수집
  ↓
모니터링
  ↓
개선
```

특히 실제 ML 제품에서는 **모델 성능뿐 아니라 데이터, 사용자, 비용, 실패 위험, 배포 환경 및 지속적인 운영까지 함께 설계해야 한다.**

따라서 모델 배포 이후 Full Stack Deep Learning을 통해 ML 제품 전체의 구조를 이해하고, 이후 MLOps를 통해 이를 안정적으로 운영하고 개선하는 것이 중요하다고 정리하였다.
