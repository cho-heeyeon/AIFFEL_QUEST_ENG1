# Day 3. 모델 테스트·트러블슈팅·성능 최적화

## Chapter 13. ML 시스템의 테스트 전략 — "소프트웨어 테스트의 다크 소울"

### ✅ Chapter 13 체크포인트

### 1. ML 테스트가 "다크 소울"이라 불리는 이유를 전통 소프트웨어와 비교하여 3가지 관점에서 설명할 수 있으신가요?

전통적인 소프트웨어는 동일한 입력에 대해 예상한 출력이 명확한 경우가 많아 `입력 → 기대 출력`을 비교하여 테스트할 수 있다.

반면 ML 시스템은 다음과 같은 이유로 테스트가 어렵다.

1. **출력이 확률적이다.**
   ML 모델은 항상 정답을 반환하는 것이 아니라 학습된 패턴을 바탕으로 확률적으로 예측한다.

2. **데이터가 프로그램의 동작에 직접 영향을 준다.**
   코드가 동일하더라도 학습 데이터나 실제 입력 데이터의 분포가 달라지면 모델 성능이 달라질 수 있다.

3. **오류의 원인을 찾기 어렵다.**
   성능이 떨어졌을 때 코드 문제인지, 데이터 문제인지, 모델 구조나 하이퍼파라미터 문제인지 바로 구분하기 어렵다.

따라서 ML 시스템은 일반 소프트웨어의 코드 테스트뿐 아니라 **데이터, 모델, 성능, 행동까지 함께 테스트해야 한다.**

---

### 2. 테스트 수트를 "분류기"로 보았을 때, 오탐(False Alarm)이 왜 위험한지 실제 사례를 들어 설명할 수 있으신가요?

테스트 자체를 정상/문제를 판정하는 분류기로 볼 수 있다.

예를 들어 설비의 정상적인 진동값 변화에도 테스트가 계속 실패하도록 기준을 지나치게 엄격하게 설정했다고 가정한다.

실제 문제는 없는데 테스트가 계속 경고를 발생시키면 개발자는 반복되는 경고를 무시하기 시작할 수 있다. 결국 실제 중요한 문제가 발생했을 때도 경고를 신뢰하지 않는 **알람 피로(Alert Fatigue)**가 발생할 수 있다.

따라서 테스트는 실제 오류를 잘 검출하는 것뿐 아니라 불필요한 오탐을 줄이는 것도 중요하다.

---

### 3. 암기 테스트(`overfit_batches=1`)가 실패했을 때 의심해야 할 원인 5가지를 나열하고, 각각의 디버깅 방법을 떠올릴 수 있으신가요?

암기 테스트는 아주 작은 데이터에 모델을 반복 학습시켜 거의 완벽하게 학습할 수 있는지 확인하는 테스트이다.

실패한다면 다음을 확인한다.

1. **레이블 오류**
   정상/이상 레이블이 올바르게 연결되었는지 원본 데이터를 직접 확인한다.

2. **입력 데이터 오류**
   Tensor의 Shape, dtype, NaN, Inf 등을 출력하여 확인한다.

3. **Loss 함수 오류**
   이진분류 또는 다중분류 문제에 적합한 Loss를 사용했는지 확인한다.

4. **학습률 문제**
   Learning Rate가 지나치게 크거나 작은지 확인하고 값을 변경하여 Loss 변화를 관찰한다.

5. **모델 또는 학습 코드 오류**
   `forward()`, `training_step()`, optimizer 설정과 gradient가 정상적으로 계산되는지 확인한다.

설비 이상예측 프로젝트에서도 본 학습 전에 소량의 센서 데이터를 모델이 제대로 암기할 수 있는지 검사하면 학습 파이프라인의 기본적인 오류를 빠르게 발견할 수 있다.

---

### 4. 데이터 기댓값 테스트에서 "느슨한 경계" 원칙이 왜 중요한지, 경계를 너무 엄격하게 잡으면 어떤 문제가 발생하는지 설명해 보세요.

실제 센서 데이터는 온도, 회전속도, 부하, 센서 노이즈 등의 영향으로 계속 조금씩 변한다.

예를 들어 정상 진동값을 정확히 하나의 값으로 제한하면 실제로 정상적인 변화까지 오류로 판단할 수 있다.

따라서 데이터 테스트에서는 물리적으로 불가능하거나 명백히 비정상적인 값을 탐지할 정도의 **합리적이고 느슨한 범위**를 설정하는 것이 좋다.

경계를 지나치게 엄격하게 설정하면 정상 데이터에도 테스트가 반복적으로 실패하여 오탐이 증가하고 테스트 자체에 대한 신뢰도가 떨어질 수 있다.

---

### 5. 행동 테스트의 "불변성 테스트"와 "방향성 테스트"의 차이를 자신의 프로젝트에 적용하여 각각 1개씩 예시를 만들어 보실 수 있나요?

**불변성 테스트(Invariance Test)**는 결과에 영향을 주지 않아야 하는 작은 변화가 입력에 발생했을 때 모델의 판단이 크게 바뀌지 않는지 확인한다.

설비 이상예측 프로젝트에서는 정상적인 센서 노이즈 수준의 작은 진동 변화가 추가되어도 `정상 → 이상`으로 예측이 갑자기 바뀌지 않아야 한다.

**방향성 테스트(Directional Expectation Test)**는 특정 입력이 위험한 방향으로 변하면 모델의 출력도 예상한 방향으로 변하는지 확인한다.

예를 들어 다른 조건이 동일하고 진동 이상 특성이 명확하게 증가하는 입력을 만들었을 때 모델의 이상 확률이 낮아지는 것이 아니라 증가하는지를 검사할 수 있다.

단, 실제 설비에서는 진동값 하나가 증가한다고 반드시 고장을 의미하지 않으므로 실제 데이터와 도메인 지식을 기반으로 검증해야 한다.

---

# Chapter 14. 모델 트러블슈팅 3단계 — Make it Run, Make it Fast, Make it Right

### ✅ Chapter 14 체크포인트

### 1. "Make it Run → Make it Fast → Make it Right" 순서에서 왜 ML에서는 "Fast"가 "Right"보다 먼저 와야 하는지 설명할 수 있으신가요?

ML 개발에서는 모델을 한 번 만드는 것으로 끝나지 않고 여러 모델과 하이퍼파라미터를 반복해서 실험해야 한다.

먼저 코드를 정상적으로 실행시키고(**Make it Run**), 그다음 학습과 데이터 처리를 빠르게 만든다(**Make it Fast**).

실험 속도가 빨라지면 같은 시간 동안 더 많은 가설을 검증할 수 있기 때문에 최종적으로 더 좋은 모델을 찾는 과정(**Make it Right**)도 빨라진다.

즉,

**실행 가능 → 빠른 반복 실험 → 성능 개선**

순서로 진행하는 것이다.

---

### 2. OOM 오류를 해결하는 4단계 전략을 순서대로 말할 수 있으신가요? Adam이 파라미터의 3~4배 메모리를 쓰는 이유는 무엇인가요?

OOM(Out Of Memory)이 발생하면 다음 순서로 대응할 수 있다.

1. Batch Size를 줄인다.
2. Mixed Precision(FP16/BF16)을 적용한다.
3. Gradient Accumulation 또는 Gradient Checkpointing을 검토한다.
4. 그래도 부족하면 모델 크기, 입력 크기 또는 시퀀스 길이를 줄이거나 더 큰 GPU를 사용한다.

Adam optimizer는 모델 파라미터만 저장하는 것이 아니라 gradient와 함께 각 파라미터에 대한 **1차 모멘트와 2차 모멘트 상태**를 추가로 유지한다.

따라서 단순히 모델 파라미터만 저장하는 경우보다 학습 과정에서 훨씬 많은 메모리가 필요하다.

---

### 3. 프로파일링 결과에서 `get_train_batch`가 전체 시간의 60%를 차지한다면 어떤 최적화를 우선 시도하시겠어요? 반대로 `training_step`이 90%라면요?

`get_train_batch`가 60%라면 **데이터 로딩이 병목**일 가능성이 높다.

따라서 다음을 우선 검토한다.

* DataLoader `num_workers` 증가
* `pin_memory` 활용
* 불필요한 전처리 감소
* 데이터 캐싱
* 저장 형식 및 디스크 I/O 개선

반대로 `training_step`이 90%라면 **모델 연산이 병목**일 가능성이 높다.

이 경우에는 Mixed Precision, 모델 구조 단순화, 연산량 감소, GPU 활용률 확인 등을 우선 검토한다.

즉 프로파일링의 목적은 추측으로 최적화하는 것이 아니라 **실제로 시간이 많이 소비되는 부분부터 개선하는 것**이다.

---

### 4. 스케일링 법칙의 "작은 실험 → 직선 외삽 → 필요 자원 추산" 흐름을 자신의 언어로 설명하고, 이것이 비즈니스적으로 어떤 가치를 주는지 설명해 보세요.

처음부터 전체 데이터와 큰 모델을 이용하여 비싼 실험을 하지 않고 작은 데이터와 모델로 먼저 여러 번 실험한다.

그 결과에서 데이터량이나 연산량 증가에 따른 성능 및 비용 변화 추세를 파악하고, 더 큰 규모에서 필요한 GPU 시간과 비용을 **대략적으로 추정**한다.

이를 통해 기업은 본격적인 개발 전에 다음을 판단할 수 있다.

* GPU가 얼마나 필요한가?
* 학습 시간이 얼마나 걸리는가?
* 비용이 얼마나 발생하는가?
* 추가 데이터가 성능 향상에 가치가 있는가?

따라서 불필요한 GPU 비용과 개발시간을 줄이고 프로젝트 투자 여부를 더 합리적으로 판단할 수 있다.

---

### 5. 성능 저하 진단표(오버피팅/언더피팅/분포 변화)에서 자신의 최근 프로젝트가 어떤 상황이었는지 분석하고 적절한 처방을 매칭해 보세요.

기존 설비 이상예측 프로젝트는 `vibration`, `error_count`, `current`를 입력으로 정상/이상을 예측했지만 학습에 사용한 데이터가 실제 설비에서 수집된 데이터가 아니라 프로젝트 실습을 위해 구성한 데이터였다.

따라서 현재 단계의 핵심 문제를 단순한 오버피팅이나 언더피팅으로 확정하기보다는 **실제 운영 데이터에 대한 일반화 성능이 검증되지 않은 상태**로 보는 것이 적절하다.

처방은 다음과 같다.

**실제 설비 데이터 확보 → Train/Validation/Test 분리 → 실제 데이터로 재학습 → 일반화 성능 평가 → 현장 데이터 분포 변화 모니터링**

이번 실행계획에서는 이를 위해 실제 베어링 시험 데이터를 활용하여 프로젝트를 발전시키는 것을 목표로 한다.

# Chapter 15. LLM 시대의 평가와 모니터링

### ✅ Chapter 15 체크포인트

### 1. LLM 기반 시스템을 Accuracy만으로 평가할 수 없는 이유를 설명하고 추가로 필요한 평가 차원을 5가지 나열할 수 있으신가요?

LLM은 하나의 질문에 여러 개의 적절한 답변이 존재할 수 있기 때문에 단순히 정답/오답만으로 평가하기 어렵다.

추가 평가 차원의 예시는 다음과 같다.

1. **정확성(Correctness)** — 사실과 맞는가?
2. **관련성(Relevance)** — 질문과 관련된 답변인가?
3. **일관성(Consistency)** — 동일한 조건에서 답변이 지나치게 흔들리지 않는가?
4. **안전성(Safety)** — 위험하거나 부적절한 답변을 생성하지 않는가?
5. **유용성(Helpfulness)** — 사용자의 실제 목적을 해결하는 데 도움이 되는가?

설비 이상예측 프로젝트는 LLM 프로젝트가 아니므로 Precision, Recall, F1-score, ROC-AUC, Confusion Matrix 등의 분류 평가 지표가 더 직접적으로 중요하다.

---

### 2. LLM-as-a-Judge의 장점과 주의할 한계(편향)를 각각 설명하고 편향을 완화하는 방법을 하나 제안해 보세요.

LLM-as-a-Judge는 사람이 모든 결과를 직접 평가하지 않고 LLM이 다른 모델의 출력을 평가하도록 하는 방법이다.

**장점:** 대량의 결과를 빠르고 비교적 저렴하게 평가할 수 있다.

**한계:** 평가하는 LLM 자체가 특정 문체, 답변 순서, 길이 등에 편향될 수 있으며 평가 결과가 항상 사람의 판단과 일치한다고 보장할 수 없다.

**완화 방법:** 일부 평가 데이터를 사람이 직접 평가하고 LLM 평가 결과와 비교하여 Judge의 평가 기준을 검증한다.

---

### 3. 입력 드리프트, 출력 드리프트, 성능 드리프트의 차이를 각각 한 문장으로 설명하고 자신의 프로젝트에서 가장 가능성 높은 드리프트 유형은 무엇인지 분석해 보세요.

**입력 드리프트:** 운영 중 들어오는 입력 데이터의 분포가 학습 데이터의 분포와 달라지는 현상이다.

**출력 드리프트:** 모델이 예측하는 정상/이상 등의 결과 분포가 이전과 달라지는 현상이다.

**성능 드리프트:** 시간이 지나면서 실제 정답 기준의 Precision, Recall, F1 등의 모델 성능이 떨어지는 현상이다.

설비 이상예측 프로젝트에서는 **입력 드리프트가 특히 발생하기 쉽다.**

베어링 마모, 설비 노후화, 센서 교체, 회전속도, 부하, 온도 및 운전조건 변화 등에 따라 진동과 전류 데이터의 분포가 학습 시점과 달라질 수 있기 때문이다.

입력 드리프트가 장기간 지속되면 출력 및 성능 드리프트로 이어질 수 있으므로 지속적인 모니터링이 필요하다.

---

### 4. "모델은 시간이 지나면 썩는다"는 말의 의미를 코로나19 같은 구체적 사례로 설명할 수 있으신가요? 이를 방지하기 위해 어떤 시스템이 필요한가요?

모델이 실제로 물리적으로 손상된다는 뜻이 아니라 **모델이 학습했던 세상과 현재 환경이 달라져 예측 성능이 떨어질 수 있다는 의미**이다.

예를 들어 코로나19 이전의 소비·교통·의료 이용 패턴으로 학습한 예측 모델은 코로나19 발생 이후 사람들의 행동이 급격히 변하면서 기존 데이터 패턴이 더 이상 유지되지 않아 성능이 떨어질 수 있었다.

이를 방지하기 위해서는 다음과 같은 MLOps 구조가 필요하다.

**운영 데이터 수집 → 드리프트 감지 → 실제 성능 모니터링 → 알림 → 데이터 재수집/레이블링 → 모델 재학습 → 검증 → 재배포**

### 2. 테스트 전략 설계

최소 테스트 목표를 다음과 같이 설정한다.

**데이터 기댓값 테스트 3개**

1. 센서 데이터에 NaN/Inf가 없는지 확인
2. 입력 Feature Shape가 모델 입력 규격과 일치하는지 확인
3. 센서값이 사전에 정의한 물리적·통계적 허용 범위를 크게 벗어나지 않는지 확인

**암기 테스트 1개**

**행동 테스트 2개**

1. 불변성 테스트 — 작은 센서 노이즈에 예측 결과가 과도하게 변하지 않는지 확인

* Confusion Matrix

특히 실제 이상을 정상으로 놓치는 **False Negative**가 설비 관리 측면에서 중요하므로 Recall을 주요 평가 지표 중 하나로 관리한다.

Human eval은 ML 모델이 이상 가능성을 예측한 경우 정비 담당자가 센서 상태 및 실제 설비 상태를 추가 확인하는 방식으로 적용할 계획이다.

# ■ 리스크와 완화 계획

### 가장 큰 리스크

PoC에 사용하는 공개 베어링 시험설비 데이터와 실제 제조현장의 센서 및 운전환경에는 차이가 존재할 수 있다.

따라서 공개 데이터에서 높은 Recall 또는 F1-score를 얻더라도 **실제 생산설비에서 동일한 성능이 보장되는 것은 아니다.**

### 완화 방법

1. 공개 시험설비 실측 데이터로 PoC 모델을 개발한다.
2. Train / Validation / Test 데이터를 적절하게 분리하여 일반화 성능을 평가한다.
3. 실제 적용 대상 설비의 현장 센서 데이터를 추가 확보한다.
4. 공개 데이터와 현장 데이터의 분포 차이를 분석한다.
5. 필요하면 현장 데이터 기반으로 모델을 재학습하거나 개선한다.
6. 현장 검증 초기에는 Human-in-the-loop 방식으로 운영한다.
7. 충분한 성능과 안정성이 검증된 이후 자동화 범위 확대 여부를 판단한다.

### 되돌아갈 수 있는 시점

다음과 같은 경우 기존 방식으로 되돌아갈 수 있도록 설계한다.

* PoC Recall/F1 목표를 충족하지 못하는 경우
* 현장 데이터와 학습 데이터의 분포 차이가 큰 경우
* 현장 검증에서 False Negative가 허용하기 어려운 수준으로 발생하는 경우
* 운영 중 성능 드리프트가 확인되는 경우

이 경우 기존 **임계값 기반 설비 모니터링 방식**을 유지하면서 데이터를 추가 확보하고 모델을 재학습한다.
