# Chapter 7. 현대적 ML 엔지니어를 위한 개발 환경

## ✅ Chapter 7 체크포인트

### 1. VS Code의 원격 개발 기능이 ML 엔지니어에게 왜 필수적인지, GPU 서버 활용 관점에서 설명할 수 있으신가요?

로컬 PC에 고성능 GPU가 없어도 VS Code의 원격 개발 기능을 이용하면 SSH 등을 통해 GPU 서버에 접속하여 개발할 수 있다.

코드는 VS Code에서 편집하지만 실제 Python 실행, 모델 학습, GPU 연산은 원격 GPU 서버에서 수행할 수 있다.

따라서 ML 엔지니어는 자신의 PC 성능에 크게 제한받지 않고 클라우드나 사내 GPU 서버의 자원을 활용할 수 있다.

**정리**

`내 PC의 VS Code → 원격 접속 → GPU 서버 → 모델 학습`

---

### 2. 주피터 노트북의 세 가지 문제점과 하이브리드 솔루션은 무엇인가요?

주피터 노트북은 실험에는 편리하지만 실행 순서, 리팩토링, 버전 관리 측면에서 문제가 발생할 수 있다.

**① 실행 순서 문제**

셀을 위에서 아래로 실행하지 않고 임의 순서로 실행하면 변수의 상태가 달라져 동일한 결과가 나오지 않을 수 있다.

→ 중요한 코드는 Python 함수나 `.py` 파일로 분리하고 노트북은 실험과 결과 확인에 사용한다.

**② 리팩토링 문제**

코드가 여러 셀에 흩어지면 함수화하거나 모듈화하기 어렵다.

→ 반복 사용되는 모델, 데이터 처리, 학습 코드는 `.py` 모듈로 분리한다.

**③ 버전 관리 문제**

`.ipynb` 파일은 출력 결과와 메타데이터까지 포함하므로 Git에서 코드 변경점을 비교하기 불편할 수 있다.

→ 핵심 코드는 `.py` 파일로 관리하고 Git으로 버전 관리한다.

즉, 하이브리드 솔루션은 다음과 같다.

`Jupyter = 탐색·실험·시각화`

`Python(.py) = 실제 프로그램·재사용 코드`

`Git = 버전 관리`

### 3. 결정적 빌드가 보장되지 않으면 팀 협업에서 어떤 문제가 발생하나요?

결정적 빌드는 같은 코드와 같은 의존성 환경을 사용했을 때 동일한 실행 환경을 재현할 수 있도록 만드는 것이다.

예를 들어 한 개발자의 환경에는 PyTorch A 버전이 설치되어 있고 다른 개발자에게는 B 버전이 설치되어 있다면 동일한 코드라도 오류가 발생하거나 결과가 달라질 수 있다.

대표적인 문제가 다음과 같다.

* "내 컴퓨터에서는 되는데 다른 사람 컴퓨터에서는 안 되는" 문제
* 라이브러리 버전 충돌
* 모델 실행 결과 차이
* 배포 서버에서의 실행 실패

따라서 Python 버전, 라이브러리 버전, Docker 이미지 등의 환경 정보를 관리해야 한다.

---

### 4. `requirements.in`과 `requirements.txt`의 역할 차이는 무엇인가요?

`requirements.in`은 프로젝트에서 직접 필요한 주요 라이브러리를 사람이 관리하는 파일이다.

예:

```text
torch
pytorch-lightning
numpy
opencv-python
```

반면 `requirements.txt`는 실제 설치에 필요한 구체적인 버전과 의존성을 고정하는 데 사용할 수 있다.

예:

```text
torch==2.x.x
numpy==2.x.x
...
```

따라서 개념적으로

`requirements.in = 필요한 패키지 선언`

`requirements.txt = 재현 가능한 설치 환경 고정`

으로 이해할 수 있다.

# Chapter 8. PyTorch 생태계 심화 — 스파게티 코드에서 프로덕션 코드로

## ✅ Chapter 8 체크포인트

### 1. 전통적인 PyTorch 학습 루프 대비 Lightning으로 전환하면 직접 작성하지 않아도 되는 코드는 무엇인가요?

대표적으로 다음과 같은 반복 코드가 줄어든다.

1. epoch 반복문
2. batch 반복문
3. `optimizer.zero_grad()`
4. `loss.backward()`
5. `optimizer.step()`

또한 GPU 이동, 체크포인트 저장, 로깅, 분산 학습 등의 반복적인 작업도 Lightning의 `Trainer`가 상당 부분 관리할 수 있다.

---

### 2. `LightningDataModule.setup`과 `train_dataloader`의 차이는 무엇인가요?

`setup()`은 데이터를 학습용, 검증용, 테스트용으로 준비하거나 분할하는 역할을 한다.

예:

```python
def setup(self, stage=None):
    self.train_dataset = ...
    self.val_dataset = ...
    self.test_dataset = ...
```

`train_dataloader()`는 준비된 학습 데이터셋을 실제 모델에 batch 단위로 전달할 `DataLoader`로 만드는 역할을 한다.

```python
def train_dataloader(self):
    return DataLoader(
        self.train_dataset,
        batch_size=32,
        shuffle=True
    )
```

이를 분리하면 데이터 준비와 데이터 공급 책임이 명확해지고 학습·검증·테스트 코드를 재사용하기 쉬워진다.

---

### 3. `_shared_step` 패턴에서 공통 로직과 단계별 차이는 무엇인가요?

학습, 검증, 테스트에는 공통으로 반복되는 코드가 많다.

예를 들어

`입력 → 모델 → 예측 → loss 계산 → metric 계산`

은 대부분 동일하다.

따라서 `_shared_step()`에 공통 부분을 작성할 수 있다.

```python
def _shared_step(self, batch):
    x, y = batch
    y_hat = self(x)
    loss = self.loss_fn(y_hat, y)
    return loss
```

그리고 `training_step`, `validation_step`, `test_step`에서는 각 단계에 필요한 로그 이름이나 추가 metric 등을 다르게 처리한다.

---

### 4. `overfit_batches=1` 테스트가 실패하면 무엇을 확인해야 하나요?

**첫째, 데이터 또는 레이블 문제**

입력 데이터와 정답 레이블이 올바르게 연결되어 있는지 확인한다.

**둘째, 모델 구조 문제**

출력 차원과 클래스 수가 일치하는지, forward 과정이 정상인지 확인한다.

**셋째, 학습 설정 문제**

learning rate, loss function, optimizer 등이 적절한지 확인한다.

하나의 batch조차 제대로 학습하지 못한다면 전체 데이터로 학습하기 전에 모델과 학습 파이프라인의 기본 오류부터 찾아야 한다.

---

### 5. 실제 프로젝트에 적용한다면 `LitClassifier.__init__`과 `MyDataModule.setup`에서 무엇을 변경해야 하나요?

샤프트 이미지 프로젝트에 적용한다고 가정하면 `LitClassifier.__init__`에서는 실제 사용할 모델 구조, loss function, learning rate, 클래스 수 등을 설정해야 한다.

`MyDataModule.setup`에서는 실제 샤프트 이미지 경로와 레이블을 읽고 train/validation/test 데이터셋으로 분리해야 한다.

즉,

`LitClassifier = 모델과 학습 방법`

`MyDataModule = 실제 데이터 구성`

으로 역할을 나눌 수 있다.

# Chapter 9. GPU 하드웨어와 클라우드 인프라의 경제학

## ✅ Chapter 9 체크포인트

### 1. 분산 학습에서 GPU 인터커넥트가 중요한 이유는 무엇인가요?

여러 GPU를 이용한 분산 학습에서는 GPU가 각각 계산만 빠르게 하는 것으로 충분하지 않고 GPU 사이에서 데이터와 gradient를 빠르게 교환해야 한다.

이를 고속도로에 비유하면 GPU의 연산 성능은 자동차의 속도이고 인터커넥트는 자동차가 이동하는 고속도로이다.

자동차가 아무리 빨라도 톨게이트와 도로가 막혀 있으면 전체 이동 시간이 증가한다.

마찬가지로 GPU 연산 속도가 매우 빨라도 GPU 간 통신이 느리면 분산 학습 성능이 제한될 수 있다.

---

### 2. GPU를 시간당 비용보다 실험당 비용으로 평가해야 하는 이유는 무엇인가요?

다음은 이해를 위한 **가상 예시**이다.

| GPU   | 시간당 비용 | 학습 시간 | 실험 1회 비용 |
| ----- | -----: | ----: | -------: |
| GPU A |     $1 |  10시간 |      $10 |
| GPU B |     $3 |   2시간 |       $6 |

GPU B는 시간당 비용이 3배이지만 학습 시간이 크게 줄어 실험 전체 비용은 오히려 저렴하다.

따라서 GPU 선택 시

`시간당 가격 × 실제 학습 시간 = 실험당 비용`

을 비교하는 것이 중요하다.

※ 위 숫자는 개념 설명용 예시이며 실제 클라우드 가격이 아니다.

---

### 3. 스팟 인스턴스를 안전하게 사용하기 위한 조건은 무엇인가요?

스팟 인스턴스는 클라우드 사업자의 상황에 따라 실행 중 중단될 수 있다.

따라서 다음과 같은 준비가 필요하다.

* 모델 checkpoint 주기적 저장
* 중단된 학습을 다시 시작할 수 있는 구조
* 데이터의 외부 스토리지 저장
* 로그와 실험 결과 저장

즉, 인스턴스가 갑자기 종료되어도 처음부터 다시 시작하지 않아도 되는 구조가 필요하다.

---

### 4. 실습에서 W&B가 있었다면 어떤 점이 편리했을까요?

Weights & Biases(W&B)를 사용하면 여러 실험의 loss, accuracy, learning rate, hyperparameter 등을 한 곳에서 비교할 수 있다.

예를 들어 YOLO 학습에서 batch size, epoch, augmentation 조건 등을 변경했을 때 각각의 결과를 자동으로 기록하면 어떤 설정에서 성능이 좋아졌는지 쉽게 비교할 수 있다.

수기로 실험 결과를 기록하는 것보다 실험 추적과 재현성이 좋아진다.

# Chapter 10. 데이터 저장과 관리의 기초

## ✅ Chapter 10 체크포인트

### 1. 스토리지 지연 시간이 `DataLoader num_workers` 설정에 어떤 영향을 미치나요?

데이터를 읽는 속도가 느리면 GPU가 계산을 끝내고 다음 데이터를 기다리는 상황이 발생할 수 있다.

`num_workers`를 늘리면 여러 worker가 병렬로 데이터를 읽고 전처리할 수 있으므로 데이터 공급 병목을 줄일 수 있다.

그러나 무조건 많이 설정한다고 빨라지는 것은 아니며 CPU, RAM, 스토리지 속도와 데이터 특성을 고려하여 조정해야 한다.

---

### 2. "이진 데이터는 S3에, URL만 DB에"라는 원칙은 왜 필요한가요?

이미지, 영상, 모델 파일 같은 대용량 이진 데이터는 객체 스토리지에 저장하고 DB에는 파일의 위치와 메타데이터를 저장하는 방식이 일반적으로 관리하기 편리하다.

예:

```text
Object Storage
shaft_001.jpg
shaft_002.jpg

Database
ID | image_url | result
1  | .../shaft_001.jpg | OK
2  | .../shaft_002.jpg | NG
```

대용량 파일을 DB 자체에 모두 저장하면 DB 크기 증가, 백업 및 복구 부담, 데이터 처리 성능 등의 문제가 발생할 수 있다.

---

### 3. OLTP와 OLAP의 차이는 무엇인가요?

OLTP는 개별 데이터를 빠르게 입력·수정·조회하는 업무에 적합하며 전통적으로 행 중심 데이터베이스가 많이 사용된다.

예:

```sql
SELECT * FROM measurement
WHERE id = 100;
```

특정 제품의 검사 결과를 조회하는 작업에 적합하다.

OLAP는 많은 데이터를 집계하고 분석하는 업무에 적합하며 분석 시스템에서는 열 지향 저장 방식이 많이 사용된다.

예:

```sql
SELECT AVG(diameter)
FROM measurement
WHERE date = '2026-08-27';
```

즉,

`OLTP = 개별 거래/업무 처리`

`OLAP = 대규모 집계/분석`

으로 이해할 수 있다.

# Chapter 11. 데이터 레이블링과 품질 관리

## ✅ Chapter 11 체크포인트

### 1. 레이블링을 최소화하는 4가지 전략은 무엇인가요?

**자기지도 학습(Self-supervised Learning)**
레이블이 없는 데이터 자체에서 학습 신호를 만들어 사전학습한다.

**데이터 증강(Data Augmentation)**
기존 데이터를 회전, 밝기 변경, blur 등의 방법으로 변형하여 데이터 다양성을 증가시킨다.

**합성 데이터(Synthetic Data)**
실제 데이터를 추가 수집하기 어려울 때 인위적으로 학습 데이터를 생성한다.

**사용자 피드백(User Feedback)**
실제 시스템 사용 과정에서 발생하는 수정이나 판정 정보를 새로운 학습 데이터로 활용한다.

샤프트 이미지 프로젝트에서는 특히 **데이터 증강**을 적용할 수 있으며 실제 촬영 데이터를 추가 확보할 수 있다면 함께 사용하는 것이 바람직하다.

---

### 2. 골드 표준 데이터셋은 왜 필요한가요?

골드 표준 데이터셋은 전문가가 정확한 기준으로 검증한 기준 데이터이다.

외주 레이블링을 맡길 경우 작업자의 판단 기준이 서로 다를 수 있다.

골드 데이터가 있으면 외주 작업 결과와 기준 정답을 비교하여 레이블링 품질을 평가할 수 있다.

골드 표준이 없다면 잘못된 레이블이 대량으로 만들어져도 이를 객관적으로 발견하기 어려워질 수 있다.

---

### 3. 약지도 학습의 유지보수 장점은 무엇인가요?

수동 레이블링은 레이블 기준이 변경되면 사람이 많은 데이터를 다시 수정해야 한다.

반면 약지도 학습에서 규칙이나 labeling function으로 레이블을 생성하도록 구성했다면 규칙을 수정하고 다시 실행하여 레이블을 갱신할 수 있다.

따라서 레이블 정책이 자주 바뀌는 프로젝트에서는 유지보수 비용을 줄일 가능성이 있다.

---

### 4. LLM 합성 데이터는 언제 효과적이며 무엇을 주의해야 하나요?

LLM은 텍스트 분류, 질의응답, 대화 데이터처럼 언어 기반 데이터가 부족할 때 다양한 예제를 생성하는 데 유용하다.

하지만 생성된 데이터가 실제 환경을 정확하게 반영한다고 보장할 수 없고 잘못된 정보나 편향이 포함될 수 있다.

따라서 합성 데이터는 실제 데이터와 분리하여 관리하고 품질 검증을 거쳐 사용해야 한다.

특히 실제 샤프트의 정밀 측정 이미지와 같은 물리적 데이터는 LLM이 생성한 데이터만으로 실제 측정 성능을 검증했다고 판단해서는 안 된다.

# Chapter 12. 데이터 버전 관리와 워크플로우 자동화

## ✅ Chapter 12 체크포인트

### 1. 현재 프로젝트의 데이터 버전 관리 수준과 다음 단계는 무엇인가요?

현재 샤프트 외경 측정 프로젝트는 GitHub에 코드와 일부 데이터 구조를 관리하고 있지만, 데이터 자체를 코드와 연결하여 완전하게 버전 추적하는 체계는 아직 제한적이다.

따라서 다음 단계에서는 데이터 파일을 단순 저장하는 것에서 발전하여 데이터의 버전, 생성 과정, 전처리 조건 등을 기록하는 방식으로 관리할 수 있다.

예를 들어 DVC 같은 데이터 버전 관리 도구를 도입하여

`Git commit ↔ Dataset version ↔ Model`

의 관계를 추적할 수 있다.

---

### 2. 데이터 버전 관리 없이 모델을 롤백하면 어떤 문제가 발생하나요?

예를 들어 모델 V2의 성능에 문제가 생겨 V1으로 돌아가려고 한다고 가정한다.

코드 V1은 Git에서 찾았지만 당시 어떤 이미지 데이터와 레이블을 사용했는지 기록되어 있지 않다면 동일한 모델을 다시 학습하기 어렵다.

즉,

`코드 V1 + 데이터 ? = 모델 V1 재현 불가`

가 된다.

따라서 모델 재현을 위해서는 코드뿐 아니라 학습 데이터의 버전도 함께 관리해야 한다.

---

### 3. Level 2 "코드로서의 데이터"의 장부 비유를 설명해 보세요.

대용량 데이터를 Git에 직접 모두 넣는 대신 어떤 데이터가 어느 버전에서 사용되었는지를 기록하는 작은 파일을 Git으로 관리하는 방식으로 이해할 수 있다.

실제 물건은 창고에 있지만 장부에는

`어떤 물건이 어디에 있고 어떤 버전인지`

기록하는 것과 비슷하다.

즉,

`실제 데이터 = 창고`

`데이터 버전 파일 = 장부`

`Git = 장부의 변경 이력`

이라고 이해할 수 있다.

---

### 4. 언제 워크플로우 자동화가 필요한가요?

작업 단계가 적고 한 번 실행하는 실험이라면 Python 스크립트만으로 충분할 수 있다.

예:

`이미지 읽기 → 전처리 → 추론 → 결과 저장`

하지만 데이터 수집, 전처리, 학습, 평가, 배포가 반복적으로 실행되고 작업 간 의존성이 복잡해지면 전문적인 워크플로우 도구가 필요할 수 있다.

예:

`데이터 수집 → 검증 → 전처리 → 학습 → 평가 → 모델 저장 → 배포`

이러한 파이프라인을 일정에 따라 반복 실행하고 실패한 작업을 재시도하거나 실행 상태를 관리해야 한다면 Airflow 같은 도구의 장점이 커진다.

# ✅ Day 2 통합 체크포인트 — 오늘 배운 것을 하나로 꿰기

## 1. 환경 점검

현재까지의 실습에서는 `requirements.txt`, 가상환경, Docker 등을 사용하여 재현 가능한 환경을 만드는 방법을 학습하였다.

하지만 완전한 결정적 빌드를 보장하려면 Python 버전과 주요 라이브러리뿐 아니라 하위 의존성, 운영체제 및 시스템 라이브러리 등의 조건도 관리할 필요가 있다.

팀원에게 환경을 전달하기 위해서는 프로젝트에 따라 다음과 같은 파일을 사용할 수 있다.

```text
requirements.in
requirements.txt
Dockerfile
.dockerignore
README.md
```

Docker를 사용한다면 실행 환경까지 컨테이너 이미지로 고정할 수 있어 재현성을 더욱 높일 수 있다.

---

## 2. 코드 리팩토링 계획

PyTorch 학습 코드를 Lightning으로 변경한다면 역할을 다음과 같이 분리할 수 있다.

### LightningModule

모델 자체와 학습에 필요한 로직을 관리한다.

```text
__init__
→ 모델, loss, learning rate 정의

training_step
→ 학습 데이터 입력
→ 예측
→ loss 계산

validation_step
→ 검증 데이터 예측
→ validation loss와 metric 계산

configure_optimizers
→ Adam 등의 optimizer 설정
```

### Trainer

실제 학습 실행 방법을 관리한다.

```text
epochs
GPU 사용
checkpoint
logging
gradient accumulation
distributed training
```

따라서 모델의 핵심 로직과 학습 실행 환경을 분리하여 코드를 더 체계적으로 관리할 수 있다.

---

## 3. 인프라 설계

샤프트 외경 측정 프로젝트를 클라우드에서 확장한다고 가정하면 다음과 같이 계획할 수 있다.

```text
개발 환경
→ VS Code

원격 개발
→ SSH

클라우드
→ GCP 등의 GPU VM

GPU
→ 데이터 규모와 모델 크기에 맞는 NVIDIA GPU

실험 관리
→ W&B

코드
→ GitHub

데이터
→ Cloud Storage 등의 Object Storage

실행 환경
→ Docker
```

현재 프로젝트 규모에서는 대규모 분산 GPU 시스템을 처음부터 구축하기보다는 단일 GPU에서 시작하고 데이터와 모델 규모가 증가할 때 GPU 자원을 확대하는 방식이 경제적이라고 판단한다.

**비용은 실제 GCP 리전, GPU 종류, VM 사양, 사용 시간에 따라 달라지므로 실제 인스턴스를 선택한 뒤 다시 계산해야 한다.**

---

## 4. 데이터 전략

샤프트 외경 측정 프로젝트에서는 실제 생산 환경에서 촬영한 이미지를 확보하는 것이 가장 중요하다.

데이터 전략은 다음과 같이 구성할 수 있다.

```text
실제 생산 이미지 확보
        ↓
정상/불량 및 ROI 레이블링
        ↓
골드 표준 데이터 구축
        ↓
데이터 증강
        ↓
Train / Validation / Test 분리
        ↓
데이터 버전 관리
```

레이블링 최소화 전략 중에서는 실제 이미지 기반 **데이터 증강**을 우선 적용할 수 있다.

다만 증강 데이터만으로 실제 현장 데이터의 다양성을 완전히 대신할 수 없으므로 새로운 촬영 조건과 불량 유형의 실제 데이터 확보가 중요하다.

데이터 버전 관리는 초기에는 데이터 파일과 생성 조건을 명확하게 기록하고, 프로젝트 규모가 커지면 DVC 등의 전문 도구를 적용하는 방향으로 발전시킬 수 있다.

---

## 5. 비용 시뮬레이션

현재 실제 클라우드 학습 시간을 측정하지 않았으므로 아래 값은 **계획 수립을 위한 가상 예시**이다.

GPU A가 시간당 $1이고 실험에 5시간이 걸린다면

```text
$1 × 5시간 = 실험당 $5
```

GPU B가 시간당 $2이지만 같은 실험을 2시간 만에 완료한다면

```text
$2 × 2시간 = 실험당 $4
```

따라서 GPU B가 시간당 가격은 높지만 전체 실험 비용은 더 낮을 수 있다.

실제 프로젝트에서는

```text
GPU 시간당 가격
×
학습 소요시간
×
실험 횟수
=
전체 GPU 비용
```

으로 계산해야 한다.

스팟 인스턴스를 사용하려면 학습 도중 인스턴스가 종료되어도 복구할 수 있도록 checkpoint 자동 저장, 외부 스토리지 저장, 학습 재시작 기능을 먼저 갖추어야 한다.

따라서 현재 단계에서는 먼저 일반 GPU 인스턴스로 전체 학습 파이프라인을 검증하고, 반복 학습이 안정적으로 재시작되는 구조를 구축한 후 스팟 인스턴스 적용을 검토하는 것이 적절하다.

# Day 2 학습 정리

Day 2에서는 단순히 모델을 만드는 것을 넘어 **같은 환경에서 모델을 재현하고, GPU를 효율적으로 사용하며, 데이터를 체계적으로 관리하고, 학습 과정을 자동화하는 방법**을 학습하였다.

전체 흐름은 다음과 같이 정리할 수 있다.

```text
개발 환경
VS Code / Remote Development
        ↓
재현 가능한 환경
requirements / Docker
        ↓
데이터 관리
Object Storage / DB / Data Versioning
        ↓
모델 개발
PyTorch Lightning
        ↓
GPU 학습
Local / Cloud GPU
        ↓
실험 관리
W&B
        ↓
워크플로우 자동화
Python Script → Airflow 등
        ↓
재현 가능한 ML 시스템
```

결국 MLOps에서 중요한 것은 단순히 **"모델이 한 번 실행되는 것"**이 아니라,

> **같은 코드와 같은 데이터를 사용하여 같은 환경을 다시 만들고, 실험 결과와 모델이 어떻게 만들어졌는지를 추적할 수 있는 시스템을 구축하는 것**

이라고 정리할 수 있다.
